# AGENTS.md — правила работы с 1С конфигурацией

## Контекст проекта

Это выгрузка конфигурации 1С:Предприятие в файлы через Конфигуратор.

Конфигурация: УТП для Украины, редакция 1.2.
Основной язык: встроенный язык 1С.
Нельзя предлагать решения как для JavaScript, Python, C#, TypeScript, React, обычного SQL или других платформ.

## Главные правила

1. Работай только в рамках текущей папки проекта.
1.1. Файлы выгрузки конфигурации использовать только для анализа. Не изменять файлы конфигурации напрямую, если пользователь явно не попросил внести правку в файлы; по умолчанию присылать код и точное место, куда его нужно добавить или доработать в Конфигураторе 1С.
2. Не предлагай функции, методы, события, объекты метаданных или свойства, если они не найдены в файлах проекта или не являются стандартными для 1С 8.x.
3. Если не уверен, что метод/свойство существует в этой конфигурации, сначала найди аналог в проекте.
4. Перед изменением кода найди похожие реализации в этой конфигурации и используй стиль проекта.
5. Для каждой доработки сначала напиши план:
   - какие файлы нужно проверить;
   - какие объекты метаданных затрагиваются;
   - где уже есть похожий код;
   - какие риски есть для типовой конфигурации.
6. После изменения покажи список измененных файлов и объясни, что именно изменено.
7. Не менять XML формы вслепую. Сначала определить тип формы, реквизиты формы, элементы формы, связанные табличные части и события.
8. Если нужно добавить поле на форму списка, сначала определить:
   - это обычная форма или управляемая;
   - используется ли динамический список;
   - откуда берутся данные списка;
   - можно ли добавить поле через запрос/реквизит/элемент формы.
9. Если нужного поля нет в источнике данных списка, не пытайся просто “заполнять колонку” на клиенте. Сначала предложи правильный способ получения данных.
10. Не использовать конструкции, которых нет во встроенном языке 1С, например:
    - `try/catch`
    - `async/await`
    - `lambda`
    - `map/filter/reduce`
    - `EXISTS` как в SQL
    - произвольные методы коллекций, которых нет в 1С
11. Не использовать возможности БСП или новых конфигураций, если их наличие не подтверждено в проекте.
12. Не предлагать расширения 1С, если задача явно про изменение основной конфигурации.
13. Не предлагать управляемые формы, если объект в проекте использует обычные формы.
14. Все примеры кода писать на встроенном языке 1С.

## Как искать решение

Перед ответом по 1С-задаче:

1. Найди объект метаданных по имени.
2. Найди модуль объекта, модуль менеджера, модуль формы или общий модуль.
3. Найди похожий код в этой же конфигурации.
4. Если задача про форму — найди файл формы и модуль формы.
5. Если задача про запрос — проверь реальные имена регистров, справочников, документов и полей.
6. Если задача про реквизит — проверь, существует ли он в выгрузке.
7. Если чего-то нет — прямо напиши: “в выгрузке не найдено”, а не придумывай.

## Формат ответа

Отвечай так:

1. Краткий вывод.
2. Что найдено в проекте.
3. Что предлагаю изменить.
4. Код.
5. Куда вставить код.
6. Что проверить в 1С после загрузки конфигурации.
7. Возможные ошибки.

## Особые правила для УТП

1. Учитывать, что это старая типовая конфигурация УТП 1.2.
2. Не предполагать наличие новых механизмов БСП.
3. Для документов проверять реальные табличные части и реквизиты.
4. Для форм проверять реальные элементы формы.
5. Для запросов использовать синтаксис запросов 1С, а не SQL.
6. Не использовать `НЕ СУЩЕСТВУЕТ`, если задача для языка запросов 1С в этой конфигурации.
7. Если можно решить задачу через запрос к регистру — сначала проверить реальные поля регистра в метаданных.

## Правило против галлюцинаций

Если я прошу добавить функционал, нельзя сразу писать код “по памяти”.
Сначала нужно подтвердить существование всех объектов:
- документ;
- справочник;
- регистр;
- реквизит;
- табличная часть;
- поле табличной части;
- форма;
- элемент формы;
- событие формы;
- общий модуль;
- экспортная процедура/функция.

Если подтверждения нет — остановись и напиши, чего не хватает.
